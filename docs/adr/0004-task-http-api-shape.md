# Versioned task HTTP API shape

The template exposes conventional versioned JSON task endpoints with explicit completion actions: `POST /v1/tasks`, `GET /v1/tasks`, `GET /v1/tasks/{task_id}`, `POST /v1/tasks/{task_id}/complete`, `POST /v1/tasks/{task_id}/reopen`, and `DELETE /v1/tasks/{task_id}`. The `/v1` prefix makes the public API contract explicit from the start while keeping operational endpoints, such as `GET /healthz`, outside the versioned task API. Completion uses action endpoints instead of generic `PATCH` so the API mirrors the domain use cases and keeps partial-update semantics out of the starter template. Successful JSON responses are enveloped by resource name, using `task` for a single Task and `tasks` for a Task collection; successful responses without a JSON body, such as `DELETE /v1/tasks/{task_id}`, remain empty. Error JSON responses use an `error` envelope containing a stable machine-readable `code` and descriptive `message`; all request body decode failures collapse to the public `invalid_json_body` code and use HTTP `400 Bad Request`, while parseable command input that violates Task rules uses HTTP `422 Unprocessable Entity`. Unexpected failures use a generic internal server error code and message. The envelope does not include metadata until the API has concrete pagination, filtering, sorting, or count semantics. Request bodies stay flat because they carry command input rather than full Task representations. `POST /v1/tasks` returns a relative `Location` header pointing to `/v1/tasks/{task_id}` because `GET /v1/tasks/{task_id}` is the canonical public URL for a task and the template should not own deployment host/proxy concerns.
