# Principal rate limits are single-instance

The gateway will enforce separate in-process token buckets for the authenticated `order-service` Service Principal: reads default to 30 requests per second with a burst of 60, and writes default to 5 requests per second with a burst of 10. A permitted request that cannot acquire a token returns `429 Too Many Requests` with `Retry-After` rounded up to the next available token and the normal `rate_limited` error envelope. Limits are configured through positive whole-number environment variables, and authentication plus scope checks happen before a request consumes quota. Rejections are measured only as `payment_gateway_rate_limit_rejections_total{route_class}`, where `route_class` is bounded to `read` or `write`; the dashboard provides an inspection panel, but no alert is set until production traffic establishes a useful threshold. Bucket state is local to one gateway process, so this policy is correct only for a single running instance; future multi-instance deployment must move principal-aware bucket state to a shared limiter while retaining this API contract. An edge limiter may add coarse volumetric protection, but is not a replacement unless it can safely authenticate the same Service Principal.
