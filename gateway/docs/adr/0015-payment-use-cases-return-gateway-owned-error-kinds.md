# Payment use cases return gateway-owned error kinds

Payment use cases return `PaymentError` values with gateway-owned error kinds instead of exposing raw adapter, storage, or bank errors. The app uses "kind" rather than "category" because these values are the small app contract, not an after-the-fact classifier over arbitrary errors. Payment errors are created through constructors so safe text is gateway-authored and causes stay private; `InvalidInput` may carry a gateway-authored reason while HTTP still renders one stable public validation message. Mock Bank and Postgres adapters translate local failures at their own boundaries, while Payment use cases translate application-rule failures and wrap any unexpected raw error as an internal Payment error before it leaves the app boundary. HTTP maps Payment error kinds to the public status, error code, and message table, so public response text does not depend on sentinel error strings or Mock Bank messages.

The initial kind set is `InvalidInput`, `NotFound`, `IdempotencyConflict`, `BankUnavailable`, `BankTimeout`, and `Internal`. `PaymentErrorKind` is string-backed for readable logs and tests. `PaymentError` fields stay private, constructors use `New...Error` names and return `error`, `Error()` returns only safe gateway-authored text, and `Unwrap()` exposes the private cause. Matching uses helpers such as `PaymentErrorKindOf` and `HasPaymentErrorKind` rather than sentinel errors or custom `errors.Is` behavior. Every exported `internal/app` function that returns an `error`, including command/query constructors and use-case methods, ensures returned errors satisfy the Payment error contract explicitly at return sites by returning a Payment error constructor or by calling `ensurePaymentError`. Exported return sites do not rely on private helper knowledge; when returning an error produced by a helper, they call `ensurePaymentError(err)` even if the helper currently returns a Payment error. Private app helpers may return local errors directly unless normalization is part of their own contract or materially simplifies callers; exported app boundaries carry the package-level guarantee. Simple validation helpers should be predicates rather than hidden error factories when the exported constructor should own the Payment error kind and message. Error-returning helpers remain appropriate for richer parsing or value construction, such as parsing a Payment ID or building card details. `ensurePaymentError` stays unexported because it is an app boundary guard, while adapters and other packages must classify known failures deliberately through Payment error constructors. Focused tests cover the exported app API boundary so helper-originated failures and raw dependency failures cannot regress into non-Payment errors.

Adapters classify dependency details into gateway semantics. Known Mock Bank invalid request responses become `InvalidInput`, insufficient funds remains a definitive declined Payment outcome, `authorization_expired` becomes an authorization-expired lifecycle signal for the application to persist as **Expired**, timeouts become `BankTimeout`, and malformed responses, unknown statuses, unknown `400` responses, random `500` responses, and other outbound transport failures become `BankUnavailable`. Mock Bank adapter failures that happen before an outbound request is validly constructed become `Internal`, because they are local gateway construction failures rather than upstream bank outcomes. Postgres not-found and idempotency conflicts become their matching kinds, while driver, scan, JSON, and invalid stored-data failures become `Internal`.

Payment use cases treat errors before and after a Mock Bank side effect differently. Before the bank accepts an operation, the use case may release the in-progress idempotency claim and return a retryable or validation error. After the bank reports a successful capture, void, or refund, local mutation or persistence failure is not handled as a simple retry path because the bank side effect may already exist; recovery must preserve the bank operation identity and avoid pretending the public command never happened.

Lifecycle conflicts are classified at the command claim boundary. Capture and void claims require an **Authorized** Payment, refund claims require a **Captured** Payment, and authorization retry claims require a **Pending** Payment with the same **Authorization Card Fingerprint**. If those preconditions are not met, the store returns `payment_status_conflict` before the use case makes a Mock Bank call. Domain invariant errors raised later inside service orchestration are treated as gateway bugs or corrupted gateway data unless a use case deliberately maps a named exception; `ensurePaymentError` is not a global domain-error classifier.
