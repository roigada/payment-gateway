# Bound synchronous payment commands to ten seconds

The gateway gives each synchronous mutating Payment command a ten-second deadline, configured as `PAYMENT_COMMAND_TIMEOUT` with a `10s` default, covering request processing, database work, Mock Bank calls, and response production. ADR-0025 supersedes this ADR's former single-call Mock Bank budget for authorization: Authorize and Authorization Retry use two-second and five-second child attempt deadlines with a cancellable 250-millisecond delay between them after a transient failure. Configuration reserves at least one second inside the command deadline for persistence after the attempts. Each child context still respects the command's remaining time. A definitive early Mock Bank availability failure returns `502 bank_unavailable`; expiry of a dedicated Mock Bank budget while the command budget remains returns `504 bank_timeout`; expiry of the command budget at any stage returns `504 payment_timeout`. Payment reads receive a separate three-second deadline, configured as `PAYMENT_READ_TIMEOUT` with a `3s` default, and return `504 request_timeout` when it expires. Operational endpoints do not use the Payment command or read deadlines: `/healthz` returns based on process liveness, `/readyz` bounds its database check to two seconds and returns `503 service_unavailable` on failure or expiry, and `/metrics` relies on connection-level limits.

The HTTP server protects its connections with positive, configurable limits: a five-second read-header timeout, fifteen-second read and write timeouts, and a sixty-second idle timeout. These network-level backstops exceed the synchronous Payment command deadline so application code can normally return a structured timeout first.

The Mock Bank HTTP transport has positive, configurable two-second connection and TLS-handshake limits, a six-second response-header limit, and a sixty-second idle-connection limit. Authorization attempt contexts provide their overall deadlines.

Request-owned work, including persistence after a Mock Bank call, continues to use the request context. The gateway does not create a detached context to complete a timed-out command; caller retry with the same Idempotency Key and the stored Bank Operation Key performs recovery. New root contexts are reserved for independently owned application lifecycles such as startup and shutdown.

The local Compose runtime explicitly supplies every non-secret timeout and database-pool setting, even when its value matches the gateway default, so the local operational contract is visible and reproducible.

The gateway emits structured JSON logs and accepts a `LOG_LEVEL` setting with an `info` default. Valid levels are `debug`, `info`, `warn`, and `error`; invalid values fail startup.

Inbound HTTP request bodies are capped by the positive `HTTP_MAX_REQUEST_BODY_BYTES` setting, defaulting to 64 KiB. Oversized bodies receive `413 Request Entity Too Large`.

Database identity remains a required `DATABASE_URL`, which contains the host, port, database name, credentials, and TLS mode. Separate `DATABASE_*` configuration only controls client-pool behavior. The pool defaults to ten maximum open connections and five maximum idle connections, uses a thirty-minute maximum connection lifetime and a five-minute maximum idle time, and fails fast when a supplied configuration value is invalid rather than silently substituting a default. Gateway startup allows five seconds, configured as `DATABASE_STARTUP_TIMEOUT`, to establish the initial database connection. Deployment sizing keeps each gateway instance's maximum open connections within the Postgres connection budget after reserved connections and all gateway replicas are accounted for; sustained pool waits are investigated with the exported pool metrics before increasing the limit.
