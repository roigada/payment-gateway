# Service-to-service Payment API boundary

The gateway authenticates the Order Service as its only **Service Principal** with opaque Bearer **Service Credentials** and authorizes Payment routes with `payments:read` or `payments:write` **Payment Scopes**. Authentication wraps the entire `/v1/` route group so new versioned endpoints are protected by default, and each route declares its required scope. The gateway configures only keyed credential digests and verifies them with a constant-time comparison; the raw credential exists only in the Order Service secret store. Missing, malformed, or invalid credentials yield `401 Unauthorized`; an authenticated principal lacking the route's scope yields `403 Forbidden`. Multiple configured active credentials permit planned rotation; emergency revocation requires a configuration rollout. Successful request logs may identify the Service Principal but never contain credential material, and metrics retain only bounded route/status labels. The OpenAPI contract, demo requests, and tests define this boundary and its failure cases. Non-local deployments must terminate TLS before the gateway; implementing that edge is a separate future job. Local Compose may use an injected throwaway development credential over HTTP and never commits it. This deliberately defers end-user, merchant, and tenant identity because the gateway has no ownership model for them; `/healthz` and `/readyz` remain probe endpoints while `/metrics` uses a separate private operational listener. The listener may bind to a network-reachable address so Prometheus can scrape it; deployments, not the application, must enforce its privacy by allowing only the monitoring network and never exposing it through a public load balancer.
