# Retry transient Mock Bank failures in request

The retry policy is introduced for Authorize and Authorization Retry in issue #116, then extended to the remaining Payment commands by later slices of issue #115. In this first slice, each authorization command makes at most two calls to the Mock Bank: an initial attempt and one automatic retry after a short fixed delay when the first call returns `bank_timeout` or `bank_unavailable`. Both calls use the already-persisted Bank Operation Key, so a retry recovers an ambiguous external outcome instead of creating a duplicate authorization. The Mock Bank adapter owns the retry policy and transport-specific attempt budgets, while the application service continues to issue one Payment operation. The retry remains owned by the incoming request and its Payment Command Timeout; it never stores Card Details or starts detached background work. Default budgets are a two-second initial attempt, a 250-millisecond retry delay, and a five-second retry attempt within the ten-second command deadline, leaving time to persist the final Payment outcome and Idempotency Replay snapshot. Cancellation of the request context during either attempt or the retry delay stops the retry immediately. The retry is transparent to callers: if both attempts fail, the gateway returns the same `bank_timeout` or `bank_unavailable` error it would otherwise have returned, and caller retry with the Idempotency Key remains the final recovery path. Existing Mock Bank RED metrics continue to count every bank call; a bounded `payment_gateway_mock_bank_retries_total{operation,result}` metric reports retry `attempted`, `succeeded`, and `exhausted` outcomes.
