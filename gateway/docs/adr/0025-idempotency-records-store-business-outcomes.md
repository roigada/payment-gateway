# Idempotency records store business outcomes, not HTTP responses

A completed public idempotency record stores the business outcome of a payment command, never a transport response. `PaymentCommandResult` carries the **PaymentResult** snapshot and, when the command completed as a failure, the gateway-owned **Terminal Failure** that caused it. It carries no HTTP status, and the `idempotency_records` table stores no HTTP status. A second protocol in front of the same use cases, such as gRPC, derives its own status values from the same record without a second snapshot format and without the application layer learning transport vocabulary.

This replaces an `HTTPStatus` field on `PaymentCommandResult` and an `http_status` column on `idempotency_records`. That design could not express a command that completed as a failure. Capture and void persist an **Expired** transition when the **Mock Bank** confirms the authorization can no longer be used, complete the idempotency record, and then return an authorization-expired Payment error. The original response was therefore a `409` error envelope, while an **Idempotency Replay** of the same key returned the stored result with no error and rendered a `409` carrying a Payment envelope. Same key, same request fingerprint, two different bodies, which contradicts the replay guarantee in ADR-0006. Storing the outcome rather than the status removes the divergence by construction: replay reconstructs the same Payment error from the stored **Terminal Failure**, and HTTP renders it through the same error mapping the original attempt used.

## A claim completes exactly when the attempt persisted a Payment transition

Idempotency protects against repeating a mutation, not against repeating work. A payment command therefore completes its public idempotency claim if and only if the attempt persisted a **Payment Status** transition, and releases the claim otherwise. `CompletePaymentCommand` is the only path that does either, and ADR-0013 already requires it to persist the transition and the replay snapshot in one database transaction, so the rule is enforced by the persistence boundary rather than by convention. No use case may complete a claim without a transition, and no use case may persist a transition without completing the claim.

The rule decides every existing path without appeal to an error taxonomy. Authorization completing as **Authorized** or **Declined** persists a transition and completes. Authorization meeting a bank timeout or an unavailable bank completes as the durable **Pending** Payment described in ADR-0022, because the **Mock Bank** may in fact hold an authorization and releasing the claim would risk a second one. Capture or void meeting a confirmed authorization expiration persists **Expired** and completes as a failure. Transient failures before any persisted transition — an unavailable bank, a timeout, a local mutation error on an in-memory Payment — release the claim so the same **Idempotency Key** may be retried and genuinely re-attempted. Validation, not-found, and **Payment Status Conflict** outcomes are detected inside the claim transaction and roll it back, so they leave no record at all and the key stays unused.

A **Terminal Failure** is therefore not a judgement about how severe an error is. It is a consequence of a state change having happened. If a future command persists a new failed lifecycle state, its kind joins the set for that reason alone.

## Only whitelisted kinds may be stored as terminal failures

`PaymentErrorKind` from ADR-0010 stays the single business error vocabulary; this decision adds no parallel enum. The set of kinds that may be persisted on a completed record is closed and small, containing only `authorization_expired` today. `IsTerminalFailureKind` is the single definition of that set, the persistence boundary validates membership on both the write and the read of a completed record, and the `failure_kind` column carries a matching `CHECK` constraint. A non-terminal kind therefore cannot be stored, and a record that somehow holds one cannot be replayed.

Rebuilding the error is a separate concern from the whitelist. `NewPaymentErrorOfKind` maps a kind to its constructor, so a stored kind yields the identical error — same kind, same message — that the original attempt returned. The capture and void expiration paths build their returned error through that same function from the same `FailureKind` they persist, so the original response and its replay cannot drift apart. Kinds whose message carries request data, invalid input and not found, cannot be rebuilt from a kind alone; they are never terminal failures, and the function reports them as internal rather than inventing a message.

The whitelist exists because the read side turns a stored string back into a Payment error. Left open, a later change that completed a claim on a transient kind would store `bank_unavailable` or `internal` and make that key replay a `502` or `500` for the whole **Idempotency Replay Window**, with no way for the caller to retry. Closing the set turns that mistake into a loud failure at the write boundary instead of a permanently poisoned record.

## HTTP derives the status from the route and the Payment Status

`internal/httpapi` owns the ADR-0006 status policy. `POST /api/v1/payments` returns `202 Accepted` when the resulting **Payment Status** is `pending`, which happens only on the unknown-authorization-outcome path, and `201 Created` otherwise. Authorization retry, capture, void, and refund return `200 OK`. Failures, replayed or not, keep the existing Payment error kind to status, error code, and message mapping. The handler compares against `domain.PaymentStatusPending` rather than its own copy of the string, so the two cannot drift into a silent `201` on a pending Payment. Public **Payment Status** values are already part of the published API payload, so reading the constant that defines them adds no coupling the payload did not already carry.
