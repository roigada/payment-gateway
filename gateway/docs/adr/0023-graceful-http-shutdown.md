# Graceful HTTP shutdown

On SIGINT or SIGTERM, the gateway becomes unready and begins stopping acceptance of new HTTP requests as it starts a configurable `SHUTDOWN_TIMEOUT` (default `30s`) drain. Request-owned work is allowed to finish during that bounded period; it continues to use its request context and may still perform its configured Mock Bank retry. Commands that do not finish before the deadline, or before a second signal forces connection closure, recover safely through existing Idempotency Key semantics. The idempotency-replay cleanup worker stops when HTTP shutdown completes, before the database closes. `GET /readyz` becomes unavailable immediately when draining starts so traffic is removed promptly, while `GET /healthz` remains successful until the process exits because it represents process liveness rather than traffic eligibility. The timeout must be a positive duration so it cannot accidentally disable bounded termination. A second SIGINT or SIGTERM skips the remaining drain period and force-closes connections, providing an operator escape hatch. Structured lifecycle logs record signal receipt, drain start and timeout, clean completion, deadline-expiration forced closure, and operator-requested forced closure; those events make deployment interruption diagnosable without adding a new metrics surface. The local Compose service uses a 35-second stop grace period, leaving a small buffer beyond the default drain window before Docker force-kills the process.
