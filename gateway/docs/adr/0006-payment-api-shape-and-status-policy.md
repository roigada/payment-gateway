# Payment API shape and status policy

The payment gateway exposes **Payment** as the public resource and keeps mock-bank operation identifiers private. `POST /api/v1/payments` creates a Payment by attempting authorization and returns `201 Created` with `authorized` or `declined`; an unknown authorization outcome returns `202 Accepted` with the `pending` Payment and its Location. Later client-driven authorization retry, capture, void, and refund commands return `200 OK` with the updated Payment. Command endpoints with no command input accept an empty request body only, rejecting any body bytes rather than accepting `{}` as equivalent input. Public errors use specific HTTP semantics: `415` for non-JSON request media types, `400` for malformed JSON or unexpected body bytes on no-input commands, `422` for valid JSON that violates client-controlled payment values such as order ID, customer ID, amount, or card details, `404` for unknown Payment IDs, `409` for invalid state transitions or idempotency-key conflicts, and `502`/`504` for unresolved bank failures outside initial authorization.

Mutating public endpoints require caller-provided idempotency keys that are scoped by operation. A repeated request with the same key and same request fingerprint replays the original response snapshot, even if the Payment has since changed; reusing the same key for the same operation with a different request fingerprint returns `409 Conflict`. Gateway idempotency keys are not forwarded to the mock bank: the gateway stores separate bank operation keys so retried provider calls remain stable across public retries.
